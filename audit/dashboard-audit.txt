PATROLBOT DASHBOARD CODEBASE AUDIT
=================================

Audit date: 2026-08-04
Scope: Entire tracked dashboard repository, including the FastAPI server,
React frontend, ROS 2 web bridge, mock robot, protocol fixtures, tests, and
Docker/nginx deployment files. The three pre-existing documentation edits in
the worktree were reviewed but not changed.

Review limits
-------------
- This was a source and local-test audit. No robot motion, live Pi/SBC access,
  remote deployment, OIDC provider, or external PostgreSQL service was used.
- Findings below are issues confirmed from reachable code paths or observed
  local behavior. Planned features such as camera video recording are not
  counted merely because they are unfinished.

Executive summary
-----------------
- P1 (high):   6 findings
- P2 (medium): 11 findings
- P3 (low):    4 findings

The highest-risk problems are stale telemetry being accepted by motion gates,
navigation health/localization checks existing only partially or only in the
browser, a Stop result being reported before Nav2 confirms cancellation, and
the production app server being reachable directly outside nginx.


P1-01 - Motion gates can authorize from indefinitely stale base/pose data
------------------------------------------------------------------------
Evidence:
- server/app/telemetry/store.py:34-46 tracks the local receipt age for each
  telemetry slice.
- server/app/commands/broker.py:231-242 builds gate facts from the last
  base_state and pose values but does not pass either slice's receipt age.
- server/app/commands/gates.py:83-84 treats the telemetry_age embedded in the
  last BaseState payload as freshness.

If the base_state or pose ROS stream stops while heartbeat/resources continue,
the WebSocket session remains online. The last payload can keep
telemetry_age=0.1 and stationary=true forever, allowing charge, motor, dock, or
undock commands from stale facts. This is especially unsafe because connection
freshness only proves that some bridge frames are arriving, not that the
motion-critical topics are fresh.

Recommendation: include server receipt age for both base_state and pose in
StateFacts, reject when either required slice is older than the gate threshold,
and add tests where heartbeat remains live while each safety stream stops.


P1-02 - Navigate can bypass hardware and localization safety checks
-------------------------------------------------------------------
Evidence:
- server/app/commands/broker.py:147-152 applies hardware gates only to commands
  listed in GATES; navigate_to_pose is not listed.
- ros2_ws/.../commands.py:151-185 checks estop, motors_enabled, and
  hardware_state_valid, but not link_connected, telemetry_age, fault_flags, or
  whether the current pose is localized/fresh.
- frontend/src/widgets/NavControlsWidget.tsx:53-57 implements the "location set
  this session" requirement only as a disabled browser button.

A crafted/stale browser frame can therefore reach Nav2 without the UI's
localization confirmation. A BaseState with a disconnected link, old telemetry,
or nonzero fault flags can also pass the bridge precheck when motors_enabled and
hardware_state_valid retain their previous true values.

Recommendation: make navigate_to_pose a server-side gate, require a fresh
localized pose and fresh fault-free base state, and repeat the same fail-closed
checks in the robot bridge. Treat the browser gate as presentation only.


P1-03 - Stop reports success before Nav2 accepts the cancellation
-----------------------------------------------------------------
Evidence: ros2_ws/.../commands.py:450-468 clears _active immediately and sends
"The robot has stopped" whenever cancel_goal_async's future completes. It never
checks the CancelGoal response or waits for the navigation goal to reach a
terminal canceled state.

If Nav2 rejects or fails the cancellation, the dashboard reports a successful
stop, discards the active goal, and ignores its eventual result while the robot
may continue moving.

Recommendation: inspect goals_canceling, keep the goal active until its result
is terminal, report cancellation refusal/failure, and only say the robot stopped
after terminal confirmation (or fresh zero-velocity evidence).


P1-04 - Production exposes uvicorn directly on every host interface
------------------------------------------------------------------
Evidence:
- infrastructure/docker-compose.production.yml:23 puts the server in host
  networking.
- infrastructure/Dockerfile.server:20 starts uvicorn on 0.0.0.0:8000.
- infrastructure/nginx/nginx.conf applies TLS and rate limits only on nginx.

Port 8000 is directly reachable wherever the host firewall allows it, bypassing
nginx TLS, request limits, and future proxy-only controls. The compose comments
also recommend a plaintext ws:// robot connection to that port, exposing the
bearer robot token to network observers.

Recommendation: use a private Compose network, expose only nginx 80/443, proxy
to server:8000, and require wss:// for robot connections outside a strictly
trusted local transport.


P1-05 - Protected browser frames are still dropped under backpressure
---------------------------------------------------------------------
Evidence: server/app/telemetry/hub.py:30-35 declares snapshots, state changes,
events, and command lifecycle frames protected, but BrowserClient.offer at
lines 53-62 ignores its protected argument and always removes the oldest item.

When a browser queue fills, ordinary telemetry can evict a command.result,
state.connection, or event frame. A lost terminal result leaves the UI showing
a command as active indefinitely; a lost connection/safety state can leave an
operator looking at stale status.

Recommendation: evict only an unprotected queued frame, track queue entries by
type/protection, and disconnect/resnapshot a client if a queue containing only
protected frames cannot accept another protected item.


P1-06 - Observer accounts can mutate global recordings
-------------------------------------------------------
Evidence: server/app/api/recordings.py:27-55 and 132-140 start, stop, and delete
recordings without a User dependency or can_command/admin check. The OIDC HTTP
middleware verifies only that a session exists. /api/commands likewise exposes
the full command audit (including usernames and source IPs) to every signed-in
observer.

The documented observer role is telemetry-only, but any allowed observer can
stop another operator's recording or permanently delete recorded data.

Recommendation: require operator permission for start/stop, administrator
permission for delete and command-audit access, and add observer-denial tests.


P2-01 - The advertised PostgreSQL deployment cannot work in the server image
----------------------------------------------------------------------------
Evidence:
- infrastructure/docker-compose.production.yml documents
  PATROLBOT_DATABASE_URL but does not pass that variable to the server.
- infrastructure/Dockerfile.server:14 installs the base package only.
- server/pyproject.toml places asyncpg in the optional "postgres" extra.

Setting PATROLBOT_DATABASE_URL in the shell has no effect on the container. If
the variable is added manually, startup imports server/app/database/pg.py and
fails because asyncpg is absent.

Recommendation: pass PATROLBOT_DATABASE_URL through Compose and install
.[postgres] in the production image; add a container-level PostgreSQL startup
test.


P2-02 - Recording replay and exports load the entire recording into memory
------------------------------------------------------------------------
Evidence:
- server/app/api/recordings.py:58-66 fetches and JSON-decodes every sample for a
  replay, although replay uses only pose, event, and battery channels.
- lines 123-129 fetch all samples and build the complete zip bytes synchronously.
- server/app/recordings/recorder.py allows 100,000 samples, with LiDAR being the
  largest channel.

A long LiDAR recording can produce a response/archive hundreds of megabytes in
size, block the event loop during conversion/compression, and duplicate the data
several times in memory. One authenticated request can freeze or OOM the server.

Recommendation: query only replay channels, paginate/stream samples, generate
zip output incrementally in a worker, and enforce response/export size limits.


P2-03 - Fire-and-forget database writes can be lost or outlive shutdown
-----------------------------------------------------------------------
Evidence:
- server/app/recordings/recorder.py:89-104 creates an untracked task per sample.
- server/app/telemetry/hub.py:176-180 does the same for battery history.
- TelemetryHub.stop closes the database without draining either task set.

Stopping a recording can return a stale sample_count while queued writes are
still pending; shutdown can close the connection under active writes, producing
unretrieved task exceptions and lost telemetry.

Recommendation: use a bounded writer queue with one owned task, flush it on
recording stop/shutdown, and surface write failures in health/logging.


P2-04 - Command audit source IP is always the reverse proxy
-----------------------------------------------------------
Evidence: server/app/websocket/ui_gateway.py:47 records websocket.client.host.
The nginx /ws/ location does not pass X-Forwarded-For, and the app does not use
a trusted proxy header even if it did.

In production every command audit identifies 127.0.0.1/nginx instead of the
operator's client, defeating the purpose of the source_ip field during an
incident review.

Recommendation: forward X-Forwarded-For/X-Real-IP in /ws/, configure a trusted
proxy boundary, and resolve the first trusted client address in the app.


P2-05 - PostgreSQL user ID allocation races concurrent first-time logins
------------------------------------------------------------------------
Evidence: server/app/database/pg.py:145-151 assigns MAX(id)+1 inside an INSERT.

Two new OIDC users logging in concurrently can select the same next id; one
request then fails with a primary-key violation instead of completing login.

Recommendation: use BIGSERIAL/IDENTITY for users.id (while retaining explicit
seed handling) or allocate through a sequence and add a concurrency test.


P2-06 - Event IDs collide when more than one robot session exists
-----------------------------------------------------------------
Evidence: server/app/telemetry/hub.py:110-115 seeds each new RobotState with the
same global value, after which server/app/telemetry/store.py:95-99 increments
IDs independently. The events table uses id alone as its primary key and SQLite
uses INSERT OR REPLACE.

With two robot IDs, their first events receive the same ID and overwrite one
another in persistence; seen-alert state in the browser also conflates them.

Recommendation: allocate IDs in the database, use a hub-global atomic counter,
or key events by (robot_id, id).


P2-07 - Negative limits bypass API bounds or fail inconsistently
----------------------------------------------------------------
Evidence: server/app/api/history.py and snapshot.py cap values only with min().
/api/commands?limit=-1 and /api/events?limit=-1 become SQLite LIMIT -1 (all
rows) and can error under PostgreSQL. Negative battery minutes are also passed
through as an invalid/unintended time window.

Recommendation: use FastAPI Query constraints with ge=1 and le=<cap> for every
limit/window parameter.


P2-08 - Battery NaN becomes invalid WebSocket JSON
---------------------------------------------------
Evidence:
- ros2_ws/.../normalizers.py:146-159 filters non-finite percentage/current but
  returns round(battery.voltage), which remains NaN for an unknown ROS reading.
- server BatteryData does not disable allow_inf_nan.
- Python json.dumps emits NaN, but browser JSON.parse rejects it.

When BatteryState.voltage is NaN, the server accepts and rebroadcasts a frame
the frontend drops as malformed, and the estimator/database can also receive a
non-finite value.

Recommendation: reject or map every non-finite numeric telemetry value before
encoding, and set allow_inf_nan=False on all protocol models containing floats.


P2-09 - Real bridge and current dock contract disagree
------------------------------------------------------
Evidence:
- Current docs/ARCHITECTURE.md and shared/schemas/protocol.md describe a working
  Dock & Charge command.
- ros2_ws/.../commands.py:318-333 explicitly omits dock capability because no
  dock-in path exists.
- CommandExecutor.handle at lines 347-373 has no dock branch.

On the real robot the frontend's Dock & Charge control remains disabled; if a
bridge ever advertises dock, the real executor rejects it as unknown. The mock
implements dock, masking the missing real path in demos/tests.

Recommendation: either implement and commission real dock-in end to end, or
remove dock from the production contract/UI/docs until it exists. Keep mock
capabilities aligned with the real bridge.


P2-10 - Server test command hangs on a supported local Python version
---------------------------------------------------------------------
Observed: `timeout 180 make test` stalled at server/tests/test_auth.py under the
repository's Python 3.14.6 environment. Re-running server tests without that
file also stalled after seven tests. The project declares Python >=3.11 and
`make setup` uses the host python3, so 3.14 is currently accepted. pyproject.toml
comments that blocked tests should fail loudly, but pytest-timeout is neither a
dependency nor configured.

Recommendation: identify/fix the TestClient/auth lifecycle deadlock, test the
declared Python range in CI, pin a supported local version if necessary, and add
per-test timeouts so `make test` cannot hang indefinitely.


P2-11 - Production lacks browser security headers
-------------------------------------------------
Evidence: infrastructure/nginx/nginx.conf sets TLS but no HSTS,
Content-Security-Policy/frame-ancestors, X-Content-Type-Options, Referrer-Policy,
or Permissions-Policy.

The command-capable dashboard can be framed by another site and receives no
browser-enforced downgrade/content hardening.

Recommendation: add an explicit header policy, at minimum HSTS after valid TLS,
frame-ancestors 'none', nosniff, a restrictive referrer policy, and a CSP tested
against the built frontend.


P3-01 - Camera gimbal authority is orphaned dead code
-----------------------------------------------------
Evidence: server/app/commands/gimbal.py and server/tests/test_gimbal.py define a
full authority/deadman system, but no protocol type, hub, gateway, frontend, or
robot bridge imports GimbalAuthority.

This creates a misleading safety surface and maintenance burden without any
runtime behavior.

Recommendation: remove it until the feature is integrated, or finish the
protocol/gateway/robot path and test the end-to-end deadman.


P3-02 - The entire docs directory is ignored
--------------------------------------------
Evidence: root .gitignore contains `docs/`. Existing documentation remains
tracked, but any new documentation file is silently hidden from git status and
easy to lose.

Recommendation: remove the broad rule and ignore only generated documentation
artifacts.


P3-03 - Frontend ships one oversized JavaScript chunk
-----------------------------------------------------
Observed: `npm run build` generated an 872.01 kB minified JavaScript chunk
(258.10 kB gzip) and emitted Vite's >500 kB warning.

Recommendation: lazy-load replay/heavy widgets and split React Query, charts,
and grid dependencies into stable vendor chunks.


P3-04 - Python builds are not reproducible
------------------------------------------
Evidence: both pyproject files use open-ended minimum versions and there is no
lock/constraints file. Docker and CI resolve different latest packages over
time; the local environment already runs newer pytest/Python combinations than
CI.

Recommendation: add a reviewed constraints/lock workflow for CI and container
builds, with a deliberate dependency update process.
